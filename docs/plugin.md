# Obsidian plugin (`packages/plugin`)

> Status: `authoritative`. The plugin is the Obsidian host of `@courier/engine`: the engine's
> rules are in [`sync-engine.md`](sync-engine.md), the scope in
> [`sync-scope.md`](sync-scope.md), the wire contract in [`api.md`](api.md). UI preview
> mechanics are in [`plugin-ui-preview.md`](plugin-ui-preview.md); copy and language rules are
> in [`i18n.md`](i18n.md).
>
> UI labels are quoted in their English form; the Chinese copy lives in the i18n catalogs.

## Build

- **Build tool is `Bun.build`** (`scripts/build.ts`), not esbuild. Output: single CJS `dist/main.js`; `obsidian`, `electron`, `@codemirror/*`, `@lezer/*` are external; `output.codeSplitting: false` keeps dynamic imports inlined into one file. The release build passes `--production` (minified, no sourcemap); a dev build keeps the inline map and copies into the vaults. `styles.css` is source, not build output: Obsidian loads it from the plugin folder, and the dev loop (`scripts/build.ts`), `setup:vault` and the e2e installer all copy it beside `main.js`.
- `manifest.json` is the Obsidian plugin manifest (`isDesktopOnly: false`), published as-is; the repository root keeps a verbatim mirror of it because the community directory reads that copy (`scripts/check-release.ts` keeps the two identical).

## Source layout and UI surfaces

- Source layout: `src/main.ts` (unified engine assembly: Obsidian lifecycle, session flows, the scope intent methods) + `src/unified/` (Obsidian vault adapter + `EngineHost` wiring the TS engine), `src/shared/` (logic the unit tests own, plus the two Obsidian-facing helpers `restore-flow.ts` and `show-notice.ts`, which the dialogs exercise end to end: `actions.ts` — the network layer over `@courier/shared`'s client, `api.ts` action types, `settings.ts`, `credential-store.ts`, `vault-credentials.ts` — the password/canary checks, `session.ts` — `unbindVault`, one teardown for disconnect/logout/vault-deleted/key-revoked, `notices.ts` — `createBurstNotifier`, `show-notice.ts` — the one `Notice` construction (Obsidian glue, exercised through the dialogs), `encrypted-path.ts` — `decryptPathOrNull`, `ui-host.ts` — the `CourierUiHost` port the dialogs depend on, `restore-flow.ts` — the shared restore interaction, `restore-name.ts` — the `-n` name rule, `recycle-bin-row.ts` — what a deleted row can do, `file-preview.ts` — how a stored version's bytes are shown, `file-actions.ts` — which Courier action a path is offered at all (none inside an excluded folder), `sync-history.ts` — the log's day/clock/label formatting, `version-history.ts` — the chain's day grouping, marker icons and size text, `sync-log.ts` — the run's in-memory sync-event store (fed by the engine, cleared on unbind/unload), `settings-stage.ts` — the settings page's step rule (`login` / `choose` / `locked` / `unverified` / `ready`) as a pure function, `file-types` labels live in the engine), `src/ui/` (the settings tab, the two main-area views — `conflict-diff-view.ts`, `version-history-view.ts` — the file explorer's chips, and the shared content renderer `file-content-render.ts`) + `src/ui/dialogs/` (every modal — the `promise-modal` base, password / setup-connection / create-vault / vault-picker / excluded-folders / sync-history / recycle-bin / file-content / conflict-replace). The split is by _kind_, never by platform: the sync path has no platform branch, and the only `Platform` reads left gate the file explorer's hover chips and choose the conflict comparison's first presentation (below), so a dialog is the same dialog on desktop and mobile. There is no WASM engine.
  - **Every read-only surface is a dialog, except the file's version history, which is a tab.** The recycle bin used to be a ribbon icon with its own sidebar `ItemView` and an `open-recycle-bin` command; it is now a row on the settings page ("Recycle bin / View") that opens `RecycleBinModal`, exactly like the sync history next to it. Clicking a row shows the version the delete removed (`FileContentModal`): markdown through Obsidian's `MarkdownRenderer.render`, other text as source, images/video/audio inline from a blob URL, and a placeholder for what has no preview (a PDF, an archive) — the rule is `shared/file-preview.ts`, built on the engine's own extension table, and the drawing itself is `ui/file-content-render.ts`, shared with the version-history view's pane. A file with no restorable version left (retention pruning) is the only disabled Restore button; a taken path is answered by a **name dialog** whose field defaults to the original name plus `-1` (`hero.md` → `hero-1.md`) (see [sync-engine.md](sync-engine.md#restore)).
  - **The version history is a main-area tab, not a modal.** `VersionHistoryView` (registered as `courier-version-history`, opened by `CourierPlugin.openVersionHistory`) puts the chain on the left — newest first, grouped by local day — and the selected version on the right: its decrypted content through the same renderer the content dialog uses (`ui/file-content-render.ts`), or a **unified diff against the version before it** (the conflict comparison's row model, `shared/text-diff.ts`). The 完整内容 / 差异 switch is the **shared segmented control** (`styles.css`) the comparison's 并排 / 统一 also uses — both answer "how do I read this page", so they are the same control in the same place. Reading a version is therefore one click, where the modal it replaced stacked a second dialog per version; selecting one repaints the pane, not the page, and the version on screen stays there until its replacement is drawn. The one write is 恢复此版本 through `shared/restore-flow.ts`, and the row for a `delete` version is a marker that cannot be selected, because the server holds no bytes for it. The tab follows the file while it is open (a debounced silent re-read on the file's vault events) and remembers the **vault** as well as the fileId, so a tab that outlives a reconnect says "not connected" instead of reading the new vault's chains. Entry points: on the desktop the file explorer's row gains a `版本历史` chip on hover (`ui/file-explorer-actions.ts`), and on a phone the `file-menu` item — labelled **Courier version history**, because the app ships its own "Version history" item on the same file — opens the same tab. Neither is offered on a **parked conflict copy**: a copy has no chain, so the entry would only open a tab with nothing in it. Neither is offered on a file under an **excluded folder** either: that folder is outside this device's scope, so the entry points follow the scope rather than the file — a chain from before the exclusion (or one the user moved into the folder) is kept, and a copy parked before it is still on disk, but none of them is offered an action from here; `shared/file-actions.ts` is the one predicate both entry points call. One tab per chain: the vault and the fileId, not the path, are its identity, so a rename does not open a second one.
  - **The sync history is this run's log, not the vault's remote history.** `SyncHistoryModal` renders `shared/sync-log.ts`: the engine's `onSyncActivity` events (a version sent, a remote version applied, or a path a **live notification** said to skip for a switch, the size cap or the API's path bound), recorded in memory as they happen and cleared on unbind and on plugin unload. Direction comes from the **operation** (a push is outgoing, an applied pull is incoming), so a device still on the default label is still read correctly; the device name is display only. A skipped row keeps the reason the engine decided at the time — flipping the switch afterwards does not rewrite a past row, which is what the old dialog got wrong when it recomputed "not synced here" from the current scope. A chain a bind/reconcile merely discovers is **not** a row: it was already on the server before this run, and logging it would repeat the same "not applied" lines on every start. The list is not fetched from `/sync/history` and has no refresh control; opening it costs no request, and it stays available while paused because it needs no vault key. Only successful sends/applies and live-notification skips are recorded: a transient failure is retried and stays in the console/Notice, so a retry cannot fill the log with attempts. The per-file version history (the file explorer's hover chip on the desktop, the file menu on a phone) and the recycle bin still read the server. Covered by `shared/sync-log.test.ts`, `shared/sync-history.test.ts`, the `onSyncActivity` cases in `engine.test.ts`, and the L2 cases that toggle a settings group after a peer's push and assert the recorded row did not change.
  - **A read-only surface takes `CourierUiHost`, not the plugin class.** The recycle bin, the sync history and the version-history view need at most four things — `settings`, `encryptionKey`, `actions`, `engine` — and they used to import `CourierPlugin` (and reach through `plugin.host?.engine`), which meant rendering a list required a whole plugin. `CourierPlugin` satisfies the port structurally, so the surfaces are testable against a plain object. The settings tab is the deliberate exception: it drives the three-step flow, so it takes the plugin and calls its intent methods (`setFileTypeEnabled` / `setSettingsGroupEnabled`, each of which saves **and** restarts the host, because the engine reads the scope when it is built) rather than mutating settings itself. The size cap is not one of those methods: it is the account's administrator-set value, read from `GET /api/me` when the host starts.
  - **The file explorer's row chips are desktop only; the same actions are in every platform's file menu.** Obsidian has no public per-file hook there, so `ui/file-explorer-actions.ts` decorates the rows: a parked copy (`isConflictFile`) gets its own small text chip (`diff` / `replace`), and every other file gets a `版本历史` chip, inserted **before** the extension tag so the tag stays the rightmost item; a file under an **excluded folder** gets neither, because this device never syncs it (`shared/file-actions.ts`, the same rule the file menu uses) — saving a new list re-decorates the rows, so an excluded row loses its chip and a newly in-scope one gets it back without waiting for a layout change; `styles.css` (shipped as a plugin file, loaded by Obsidian) keeps them muted and visible only on the row the pointer or the keyboard is on (the conflict chip also on the active or selected row) — the conflict chip sits in the row's flow, the history chip is laid over the row's right end, because reserving its width on every row would truncate file names for a button most rows never show. Following the explorer is a `MutationObserver`: a mutation **inside** a row re-decorates that row — what catches Obsidian replacing a row's children, which would otherwise leave a once-decorated row without its button — and added subtrees are searched for rows that arrived whole; `layout-change` re-attaches and `window-open` picks up a popout's tree. The conflict action is also registered on the `file-menu` event, the public fallback if the DOM ever stops matching (the failure mode is a missing chip, never an error). `CourierPlugin` installs the chips only when `Platform.isDesktop` — hover is a pointer gesture — while the surfaces themselves open on both platforms: a phone reaches the version history and a parked copy's comparison/replace from the long-press file menu, and the comparison lays itself out as one column there (`defaultConflictDiffMode` and the `body.is-phone` rules in `styles.css`; see the conflict paragraph below). Both actions only reach files in the **vault index** — the config folder is not in it, and a config-folder conflict no longer parks a copy at all (it is settled by modification time; see [sync-engine.md](sync-engine.md#conflicts)), so there is nothing under `.obsidian/` for these actions to miss. Which action a copy gets is decided by the **preview kind**, not by "is it markdown": text (`md`, `.canvas`, json, css, txt) opens `ConflictDiffView` — a **main-area tab** (`ItemView`, registered as `courier-conflict-diff` and opened with `workspace.getLeaf("tab")` + `setViewState`, so it fills the leaf the way a file view does instead of floating over the note; one tab per parked copy, recognised by the copy's path in the leaf state so a background/deferred tab is reused too, and an Obsidian layout saved with one on disk restores it because `setState` and `onOpen` are order-independent) — a read-only line diff (`shared/text-diff.ts`, a bounded LCS with no new dependency; a pair too large to align says so instead) whose layout is the shared 并排 / 统一 segmented control, with both files named in the header above it and nothing else on the desktop (a phone adds the icon tile and the legend), re-reading on `vault.on("modify"/"delete"/"rename")` with a 200 ms debounce — a side that is gone (deleted, or renamed away from the path the copy was parked beside) collapses the whole view to **one sentence naming that file** and why it may be missing, with no picker, no column names and no dump of the side that is left, because all of those describe a table that cannot be drawn; only the missing-**original** case keeps its Restore as original action, the one door that writes the copy's bytes back to its own path. The header is **one band**: the note's name with the copy's name under it on the left, then the `+n` / `−n` line counts, then Split / Unified as the **shared segmented control** (one control's width, both states in it) and Replace current file with conflict copy at the right end — all vertically centred on the names' block, built on a settings row with no border, padding or margin of its own because Obsidian gives one a margin under it. The bottom band is gone: there is no Open copy / Open current file and no Close (a tab is closed by its tab header), so the only control that writes is the replace button in the header. Below 520 px of **container** width (`container-type: inline-size` on the page) the header reflows — the names take a row, the counts and the two controls take the next — because a 379 px pane used to clip the replace button; row text wraps between words (`overflow-wrap: break-word`), never mid-word. On a **phone** the page is one column: the comparison opens in the **unified** presentation (`defaultConflictDiffMode(Platform.isPhone)`), the header becomes a card — a tinted diff tile beside the two names, the counts as pills, the layout control at their right end, and the write as a full-width 46 px band under them — and a legend above the rows names the two sides (`conflict copy` / `current file`), which a one-column stream has no column headers to carry. The split presentation stays available for short lines, with a narrowed line-number gutter and a rounded frame; these are the `body.is-phone` rules, not a second view. The two columns' gutter is one line drawn over the body (`.courier-diff-body.is-split::after`), so it runs the **box's** full height even when the note is three lines long — while media and binaries open `ConflictReplaceModal` — one sentence saying which file the copy's content becomes, and one `Delete the conflict copy after replacing` toggle (off by default: the parked copy is the only local record of the losing version) on **the buttons' own row**, its switch before the words it explains and the buttons on the right; that row is built from `ToggleComponent`/`ButtonComponent` rather than a `Setting`, whose `border-top` under the sentence read as an underline of it, and its spacing is the app's **own confirmation dialog's**, measured from `Delete file`: the sentence keeps Obsidian's `1em` paragraph margins, the row starts `1.5em` below it, and the row itself is an 8px-gap flex row with the choice taking the room the buttons do not. On a phone the same dialog stacks into one column — the choice becomes a 44 px touch row and the two buttons split the width under it — so the confirmation reads as one decision on a narrow screen. **There is no merge** and no "open both files": deliberately, the engine's rule is that the remote version won, and the only write either dialog offers is `Replace current file with conflict copy` (`Restore as original` when the original is gone — a peer's delete, or a rename), which puts the copy's bytes at the original path through `app.vault` as an **ordinary user edit**: the engine sees the vault event and pushes a `modify`, or creates a new chain when the path's chain is a peer's tombstone. The copy is deleted only when that toggle was switched on and a write actually landed (best-effort: the replaced content is already at the original path, so a copy that refuses to disappear is a leftover, not a failed replace), and both surfaces need no vault key, no engine and no network. A finished replace and Close both **detach the tab** (`Modal.close()` was what the dialog did). Unlike VS Code's editor-inline diff marks, nothing is drawn into the note's own editor: a plugin cannot decorate a code mirror the app owns, and replacing the text view would mean rebuilding the editor (live preview, undo, search) — the tab beside the note is the deliberate shape. The original path comes from `originalPathOfConflictFile` (the inverse of `conflictFilePath`, in `conflict-file.ts`); a `.md` copy also tries the extension-less reading, because `README` and `README.md` park under the same name. `styles.css` owns the view's geometry, and several of its rules are platform facts rather than taste: the layout picker is **one control wide** — its Layout label is not drawn (the two option words say what it is) and the control group carries that name as its `aria-label`, while Obsidian's default `flex: 1` on `.setting-item-control` is overridden so the control does not stretch across the row — below **520 px of container width** the header reflows (the names take a row of their own, the counts and the controls the next, the controls kept at its right end) instead of clipping the replace button — on a **phone** the `body.is-phone` rules turn the header into a card with a full-width write and show the legend, so a one-column page still says which side is which — and **the rows scroll while the tab does not**, because a view's content element is the leaf's scrollable body: `.courier-conflict-diff` is given the leaf's height (`height: 100%; min-height: 0; box-sizing: border-box`), everything but `.courier-diff-body` keeps its natural height, and only the rows inside it scroll, so the header and the two file names stay on screen when a long note is compared. The desktop geometry is asserted by pixel in the real-Obsidian case, the one layer that can see styles.

## Dev loop and test vaults

- **Dev loop / development vaults**: `bun run dev` provisions the checkout before the watcher starts. `scripts/dev-setup.ts` creates the two vaults, enables the plugin in each (`community-plugins.json`), registers them with Obsidian when the app is closed (it reads its vault list only at startup), and — once the dev server answers — mints an `ak_` host key, a `ck_` user and that user's vault, then writes the sign-in into each vault's `data.json`. When Obsidian is already running, `scripts/open-vaults.ts` opens a vault the app does not know **through the app** (`vault-open` over the renderer's IPC), which registers it without a restart — so a worktree's dev loop no longer needs every Obsidian window closed. It is idempotent and remembers itself in the gitignored `.courier-dev/dev.json`; a vault already signed in **elsewhere**, or already connected to this dev vault, is left untouched (paused state and device label included), so a rerun only provisions what is missing. Names and paths come from `scripts/dev-vaults.ts`: the primary checkout keeps `vault_a` / `vault_b`, a linked worktree gets `vault_a-<worktree>` / `vault_b-<worktree>`, because Obsidian routes `obsidian://open?vault=<name>` and the CLI's `vault=<name>` **by name** and two checkouts must not compete for one (`COURIER_OBSIDIAN_VAULT_A`/`_B` override the name). `scripts/open-vaults.ts` opens that pair (skip with `COURIER_DEV_OPEN_VAULTS=0`), turns **Restricted Mode off** in each — a vault Obsidian has never seen blocks community plugins whatever `community-plugins.json` says — and stores the remembered vault key through the CLI, so both vaults sync without a password dialog. `bun scripts/build.ts --watch` then watches: every rebuild re-copies the output into both vaults and hot-reloads the plugin **without restarting Obsidian** (`obsidian plugin:enable/reload id=courier vault=<name>`; disable with `COURIER_DEV_RELOAD=0`, and a failure only warns). `bun run --filter @courier/plugin setup:vault` is the same install without the watcher or the account. Other knobs: `COURIER_DEV_SETUP=0` skips provisioning, `COURIER_DEV_SERVER_URL` and `COURIER_DEV_VAULT_PASSWORD` replace the defaults (`http://localhost:3002`, `courier-dev`).

## Vault writes and the settings page

- All vault file mutations go through the plugin's TS engine (the engine's adapter writes decrypted pull results and parks `*.conflict.*` copies when a conflict is resolved) — never raw plugin writes that bypass the engine, to keep state consistent. The one write the conflict dialogs offer goes through `app.vault` on purpose, because it is a **user edit** and the engine's job is to see it as one (see [sync-scope.md](sync-scope.md#conflict-copies)). Settings files differ in _which_ Obsidian API is used, not in who writes them: a path inside `vault.configDir` goes through `vault.adapter` (`list`/`exists`/`readBinary`/`writeBinary`/`remove`/`rename`/`mkdir`), because Obsidian keeps that folder out of its index — `getAbstractFileByPath` answers `null` for `.obsidian/app.json` and `createBinary` would put a config file into the note tree — and its writes fire no vault event, which is why a local settings change is picked up by the host's poll (see [sync-scope.md](sync-scope.md#ownership-and-the-predicate)). `CourierSettingTab` (`src/ui/settings.ts`) shows the flow in **three steps**, derived from real state on every render (`stage()`: no `userKey` → `login`; no `connectedVaultId` → `choose`; `syncPaused` → `ready`; `encryptionKey` in memory → `ready`; otherwise `unverified` when this device holds a stored key — the key is here and only its server check is missing, so the step offers a retry — and `locked` when it holds none, which offers the password dialog) — there is no persisted session flag and no tab-local step counter beyond the `showLogin` override a **failed** sign-in sets (the key is saved before it is proved, so without it the page would already be on the vault step). The page has **no title and no step counter** — the controls say what they are. Step 1 is a plain web-style login form: nothing but two labelled full-width fields (`Server address`, `User key`) above one full-width `Sign in` button, in one 360 px column centred in the pane, built from raw DOM rather than Obsidian's settings rows, which put the label left and the control right; Enter submits (`CourierPlugin.signIn()` saves them, proves the key with the `GET /api/me` read the account row needs anyway, and keeps the account name as `settings.userName`); step 2 is two rows — the account (the name that key belongs to, the server it belongs to, and Sign out as its only action, a red `setWarning()` button) and Choose a remote vault, whose Choose button opens `VaultPickerModal` (`src/ui/dialogs/vault-picker-modal.ts`): the account's vaults, one row each — a tight, rule-less line with the name, how old it is (`src/shared/relative-time.ts`), deleting as a ✕ icon button and Connect as the row's action — plus a centred Create remote vault entry — so the page stays two rows however many vaults exist. Connecting a vault this device has not configured opens `SetupConnectionModal` (`src/ui/dialogs/setup-connection-modal.ts`): one form for the password, the per-vault device label and the folder-scope draft, with `Start syncing` owning the connect action (a failure keeps the dialog open and everything typed). A returning vault opens the same form prefilled from its record (the lead line then says the connection settings are being confirmed); deleting a remote vault — from the picker or through the server's deletion event — forgets that record. A successful connect closes the picker and re-renders the page onto step 3; **creating does not connect** (`CourierPlugin.createVault` only creates — the new vault appears in the list and the user decides when to connect to it), and a failure is shown inside the dialog, which stays open; step 3 is the actual settings, in sections — This device (the device label, first), Remote vault (connection status + a Sync row whose one button pauses or resumes syncing + Disconnect + the remembered password), File types, Obsidian settings sync, a Sync history row whose View opens `SyncHistoryModal`, and Account last (the account name, the server, and the red Sign out, all on one row). `disconnectVault()` returns to step 2 (the key stays); `logout()` clears the key, the binding and the stored key and returns to step 1 (the server URL and device label stay). The `locked` step shows nothing but `Unlock with password` + Disconnect / Sign out; the `unverified` step — the key is saved here and only its server check is missing — shows `Retry` + the same two escapes instead, because a password could not be proved either. Every section explains itself through an info icon + tooltip (`renderSection`: `Setting.setHeading()` + `addExtraButton`) instead of a paragraph, and every switch carries exactly one short line under it — what the category covers, or which config file the group owns — never a list of extensions (`file-types.ts` keeps that table). Every scope toggle saves, calls `restartHostForScope()` (the engine and the adapter read the scope when they are built) and deliberately does **not** re-render the page. The host's own state changes repaint only the status bar and the connection row's state line (`refreshLiveState` → `CourierSettingTab.refreshConnectionState`); a full `refreshSettings()` belongs to an action that changes the page's rows or step (bind, unlock, pause/resume, disconnect, logout, an applied excluded-folder list). Every user-facing failure comes back as `{ ok: false, error }` (`ActionOutcome` in `src/shared/action-error.ts`, where `describeActionError` maps 401 / `KEY_EXPIRED` / 404 / 422 / a transport failure to a sentence the page renders under the step that failed — the page never changes step on a failure, so nothing typed is lost); only background events (a resolved conflict, a vault deleted elsewhere) still use Notices. `unlockWithPassword()` **verifies the typed password against the server canary before starting the host** — a mistyped password used to derive a key and push content the real password could never decrypt. The device name is a plain debounced local save with no submit button (`CourierPlugin.setDeviceName`, `DEVICE_NAME_DEBOUNCE_MS`), and the sync history is a dialog (`SyncHistoryModal`, `src/ui/dialogs/`) opened from a page row. It is the recycle bin's shape — a header stat over one framed scroll area (`styles.css`, `.courier-history*`) — not the bare monospace dump it used to be: one row per event, grouped by day with the newest day at the bottom and each day header `sticky` while its own rows scroll past (`groupSyncHistoryByDay`, `formatHistoryDay` — Today / Yesterday / the date). A row is three parts with one job each: a **direction arrow** (`arrow-up` green = this device uploaded it, `arrow-down` blue = it arrived from another one — the colour _and_ the glyph, so the meaning survives a monochrome theme), the path with its clock reading and device under it, and the action word on the right. The direction is `syncDirectionOf(entry, deviceName)`: the server records only the label the pushing client declared, so an event whose label matches this device's is an upload, another label is a download, and the answer is `unknown` when it cannot be either — the device still carries `DEFAULT_DEVICE_NAME` (`My Device`, so two fresh installs state the same label and matching proves nothing; this is the default configuration, not an edge case) or the version has no label at all. `unknown` renders a neutral right arrow and claims nothing. The remaining limit is a display heuristic, not an identity: a renamed machine has its older rows read as incoming, and two machines given the same non-default name cannot be told apart. The list is built from `src/shared/sync-history.ts` (`flattenSyncHistory` capped at `SYNC_HISTORY_LIMIT`, `formatClockTime` for the locale-independent clock reading, `syncHistorySummary` for the header's count/label/truncation note) with the stored paths decrypted by the vault key. The list is **not** filtered by this device's scope — it describes the remote vault, and a chain only a peer carries is what explains a file that is missing here; a row the scope leaves out instead carries one quiet line naming the switch (`outOfScopeReason` → `outOfScopeLabel`: excluded folder, file type, settings group, or size cap). The reason is recovered by asking the engine's own `isSyncablePath` first and then the narrower `isConfigPath`/`isExcludedPath` questions in the engine's order (plus `withinFileSizeCap` from the version's `sizeBytes`), so the line and the sync behaviour cannot disagree; the scope comes from `syncScopeOf(settings, configDir)`, the same function `EngineHost` builds its engine from. It re-reads on two triggers: `HISTORY_REFRESH_MS` (a 10 s backstop, for a change this device never hears about) and `onSyncActivity` (`src/shared/sync-activity.ts`), which is what makes the log catch up with the sync the user is watching. The signal is raised in `EngineHost.persistState` — the one point every accepted push and every applied pull passes through — and only when the serialized state actually changed, so a five-minute reconcile that found nothing reports nothing. It is debounced by `ACTIVITY_DEBOUNCE_MS` (250 ms), because a burst (a folder of notes, a first bind) reports once per file and one request that already sees the whole change is better than ten; the dialog unsubscribes on close, and a listener that throws is logged and skipped for that report, so it can never fail the sync that reported it. Without this, a note the user watched arrive sat unlisted for up to ten seconds — the log is the one surface where 'I saw it sync' and 'the log says nothing yet' is the whole complaint. It follows the newest line whenever the view sits at the end — scrolling back to read a line keeps the position, and the position survives a repaint — and only the **first** read paints a skeleton: a refresh keeps the rows on screen, and a failed refresh keeps them too (the error moves into the header's note line) instead of replacing a readable log with an error page. The header's count is a number, never a template: it renders `syncHistorySummary(total, shown)`, because the dialog once shipped showing the literal Chinese template for “{total} sync events.” — a summary template rendered without its `{total}` parameter is still a sentence, so every assertion that only looked for the surrounding words passed. The stored scope record is normalized on load (`loadSettings`), so a missing or unknown group reads as off.

## Credentials

- **A bound vault's derived key is kept device-locally, so reopening Obsidian needs no password.** Unlocking stores it through Obsidian's App-level `localStorage` (`src/shared/credential-store.ts`) — deliberately **not** `plugin/data.json`, which lives inside the vault: any vault-level syncing (iCloud/Dropbox/Git/Obsidian Sync) would carry the key off the device and defeat the content encryption. Same path on desktop and mobile.

## Notices

- **A Notice is reserved for an event the user did not start, and that no persistent surface will show them.** The plugin is meant to be unobtrusive, so the rule is enforced rather than assumed:
  - **The result of the user's own click belongs to the surface they clicked in.** Pause / resume, disconnect, sign out, "clear saved password", create / delete a remote vault, clearing the recycle bin and replacing a file with its conflict copy all re-render the page, picker or list that was clicked; each used to add a toast that repeated the new state, and none does now. `startHost()` therefore has no `quiet` option — there is no "connected" toast to suppress, and a start with a usable stored credential is completely silent.
  - **An error caused by that click stays inline in the dialog that caused it**, never in a toast that outlives the dialog: the password prompt, create-vault and excluded-folders dialogs use `.courier-setup-error` (+ `.is-visible`), and the recycle bin has its own line under the list. This is the same principle `shared/action-error.ts` states for the settings page (`ActionOutcome` instead of a Notice), and it is why the vault picker takes `fetchVaultCredentials` — a boolean made an unreachable server read as "wrong password".
  - **Background events keep their Notice**: a conflict the engine resolved (one line per burst, naming the parked copy), a remote vault deleted, a user key revoked / expired / disabled (over the WebSocket or on a `401`/`403` from a pass), a failed first bind, a failed start, an unreachable server at launch, a dead stored credential, and the answer to a click that needs an explanation (version history / recycle bin while paused, a file with no sync record, a restore that failed).
  - **A dead credential stops the host, and what happens next depends on why.** The engine reports all three through `onAuthFailure(reason)`. `revoked` (the account was deleted, and its vaults with it) unbinds the vault and forgets the key, like a sign-out. `expired` and `disabled` **pause** instead: the binding, the stored credential and the in-memory vault key stay, the status bar reads 同步已暂停, and 恢复同步 brings it back once the administrator has fixed the key — no password prompt, and nothing to re-enter. Covered by `plugin.e2e.test.ts` (disable a hosted plugin's account: paused, still bound, one notice, then resumes) and `packages/engine/src/host.test.ts` (the callback and the stop).
  - **An event a pass re-reports carries `keyOf`.** A file over the size cap is reported by every reconcile (the engine resets its per-pass set), so `createBurstNotifier` drops an identity it has already announced for the session: one line per file, not one line every five minutes. `shared/notices.test.ts` pins both the window and the dedupe.
  - Covered by `shared/notices.test.ts`, `shared/conflict-replace.test.ts`, and the L2 cases that assert the state change instead of the toast (`plugin.e2e.test.ts`: a silent second start, a silent cancel of the resume prompt, one size-cap line across two passes, no success line after a conflict replace).

## Pause and disconnect

- **Pausing sync keeps the vault bound; disconnecting does not.** `CourierPlugin.pauseSync()` sets `settings.syncPaused`, persists it and stops the host — no vault events, no timers, no WebSocket — while keeping the binding, the in-memory key, the stored credential and the sync state, so nothing leaves or enters until the user resumes. `startHost()` refuses to start while the flag is set (the one invariant, whichever path asks) and answers whether it did start; success is never announced (see the Notice rule above). `resumeSync()` takes the flag off **only after it holds a key**, then starts the same host: the key normally survives a pause in memory, while after a restart `onload` deliberately does not unlock a paused vault (no password, no network) and the resume takes the same canary-checked key path a cold start does (`acquireVaultKey`: the device's stored credential, or the password dialog), so a cancelled dialog or an unreachable server leaves the flag set instead of silently re-enabling sync. Because a paused load never unlocks, the page can be on screen without the key: its recycle-bin row then reads resume sync and unlock the remote vault to view and is disabled (it decrypts stored paths, so opening it would render `[Unknown path]`); the sync-history row needs no key — it renders the run's in-memory log — and stays available. The remembered-password line says Resume sync unlocks it rather than reopen Obsidian, and an engine-dependent action (restore) says Sync paused instead of Not connected. `bindVault()` clears the flag (connecting a vault always starts syncing) and `unbindVault()` clears it with the binding. `disconnectVault()` remains the flow that forgets the credential. The settings page's Remote vault section carries the one row it is driven from (`Sync` row with a Pause sync / Resume sync button); the connection row keeps its single Disconnect action. Covered by `shared/settings-stage.test.ts` (a paused page is `ready`, never `locked`), `shared/session.test.ts`, and the pause/resume cases in `plugin.e2e.test.ts` (both directions stop while paused, resume catches up, a paused reload starts no host and asks for nothing, and a resume that cannot get a key stays paused).

## Status bar

- **The status bar is the always-visible sync surface, and its menu is Obsidian's own `Menu`.** One icon sits bottom-right and shows one of five states, derived in `shared/sync-status.ts`: **Not connected** (no bound vault or no key), **Pause sync** (bound and `syncPaused`), **External sync service is syncing** (bound, but the CLI holds this vault's sync lease), **Syncing** (host running and either the WebSocket is subscribed **or its first pass is still running**), and **Not syncing** (bound but locked/connecting/error/stopped). The state is carried by the icon and its theme colour; no text is put beside it, and nothing animates — `Syncing` is a connection state, not a per-file spinner. A bind counts as syncing because it runs _before_ the socket exists: a first connect of a large vault used to show the red not-synced icon for the whole pass, which reads as a fault. **The first pass's counter goes in the tooltip** (`aria-label`, which Obsidian also shows on hover): `status.tooltipFirstSync*` renders `done / total` from the engine's `onProgress`, only while `EngineHost.firstSync` is true and only until `done === total`. `firstSync` is narrower than "the host is binding": every Obsidian start runs a bind pass, but only a vault whose bind has never **completed** is meeting the remote for the first time, so a restart shows "Syncing" without a counter. That completion is persisted beside the engine's `localVersions` (`settings.syncState.bindCompleted`, written once by the host) instead of being inferred from the state being empty: a first bind killed after persisting part of a large vault leaves state behind, and its next start must keep the counter. `statusTooltip` (`shared/sync-status.ts`) also drops the counter at `done === total`, the engine's own "the pass finished" signal, so a completed bind does not leave "10 000 of 10 000" on the icon. The lease wait is reported only when it begins and ends: the retry loop reports nothing in between, so the lock icon does not flash against the red not-synced one while another writer holds the vault. `ui/status-bar.ts` owns the element and the click menu; `main.ts` creates it in `onload`, destroys it first in `onunload`, and `refreshSettings()` now repaints both the page and the icon (plus `stopHost()` and a failed `startHost()`). **The menu is forced onto Obsidian's DOM implementation (`Menu.setUseNativeMenu(false)`) and anchored to the item's own box** (`showAtPosition({ x, y, width, overlap: true })`), not shown at the mouse event. Obsidian uses **native** menus on macOS by default, and a native menu cannot draw this menu: the storage row is an element (a bar), not a label, and the read-only rows' typography is `styles.css`. It is also positioned at the pointer, so from a status bar at the very bottom of the window it hung over the window's corner instead of above the icon — which is what the macOS bug report saw. The DOM menu flips above the anchor and pulls its right edge onto the item's, so the placement is the same on every platform, and the L3 menu assertions (`.menu .menu-item`) can read it on macOS at all. The menu is deliberately terse: the vault name alone (the icon already carries the state), the remaining validity as its own value (the key icon names the row), a storage row of a quota bar plus `used/limit` built as a `DocumentFragment` (`storageMenuValue` owns the percentage and clamp; `shared/account-status.ts`), a pause/resume row for `syncing`/`waiting`/`paused`, and a `Settings` / `Settings` row that opens this plugin's tab through the non-public `app.setting.openTabById`. The read-only rows carry a `courier-status-menu-row` wrapper (the storage row its own `courier-status-menu-storage` class) so `styles.css` can give them the same size, weight and colour as the actionable rows — Obsidian's own `is-label` style is larger and muted. A vault-less menu omits the header row rather than inventing a state label. The settings page repeats the same two account readings in its account row's description for mobile, where no status bar exists: key validity as the local date plus the same countdown, and storage as the same bar plus `used/limit`, filled by the one `GET /api/me` read that already names the account (`shared/account-status.ts`'s `keyExpiryDate`, `ui/storage-usage.ts`'s `storageUsageTitle`). The section deliberately stays one row: the description is a small stack, and signing out remains the last row's action. Account values are read on each opening from `GET /api/me` with a 1.5 s cap, cached in memory per key and **never** written to `data.json`, with a read failure shown inline rather than as a `Notice`. Account and status copy live in the i18n catalogs. The element and its menu are outside `preview:ui`; L3 reads the real `status-bar-item` (geometry, state/icon attributes, `aria-label`) and the real menu labels. Covered by `shared/sync-status.test.ts`, `shared/account-status.test.ts`, the status-bar cases in `plugin.e2e.test.ts`, and the final real-Obsidian case in `sync.obsidian.test.ts`.
